# Agentic RAG 工程化迭代路线

> 把一个"能在本机跑的 RAG 应用"升级为"具备真实工程能力的完整项目"。
> 目标架构：前端(Nginx) → 后端(FastAPI + LangGraph) → 数据库(PostgreSQL) + 缓存(Redis)，全部由 docker-compose 一键启动。

```
              浏览器
                │
                ▼
        ┌───────────────┐
        │  web (Nginx)  │  容器1：托管前端页面 + 反向代理 /api
        └───────┬───────┘
                │
        ┌───────▼───────┐
        │  api (FastAPI)│  容器2：RAG 检索 + LangGraph 编排
        └───┬───────┬───┘
            │       │
      ┌─────▼──┐ ┌──▼─────┐
      │  db    │ │ redis  │  容器3、4：持久化 + 缓存
      │ (PG)   │ │        │
      └────────┘ └────────┘
```

## 阶段 ① Docker 化部署 ✅ 已完成

### 做了什么
- 后端 `Dockerfile`：基于 `python:3.11-slim`，层缓存优化（依赖与代码分层），CPU 版 PyTorch 裁剪。
- 前端 `web/Dockerfile`：多阶段构建（Node 打包 → Nginx 托管），最终镜像仅含静态产物。
- `web/nginx.conf`：托管静态页 + 反向代理 `/api` 到后端 + 支持 SSE 流式 + 放开上传体积限制。
- `docker-compose.yml`：编排 `api` 与 `web` 两个服务，含 healthcheck 解决启动时序依赖。
- 模型 / 索引 / 数据 / 结果通过挂载（volume）与镜像分离。

### 解决的问题 & 作用
| 作用 | 说明 |
|---|---|
| **环境可复现** | 任何机器 `docker compose up` 即可运行，告别"在我电脑上能跑" |
| **一键启动** | 一条命令拉起前后端，替代手动启动多个服务 |
| **镜像与数据分离** | 代码进镜像、模型/数据挂载，镜像小、数据可独立更新 |
| **部署标准化** | 与生产部署方式一致，可直接迁移到服务器 / 云 |

### 💡 一句话作用（大白话）
**把"只能在你电脑跑"变成"在任何机器一键就能跑"。**
- 以前换台电脑要重装 Python、装一堆依赖、配环境，各种"在我这能跑你那跑不了"；现在 `docker compose up` 一句话，前后端全起来，环境完全一致。
- 这是**工程化的地基**——后面加数据库、缓存，都只是往 compose 里再加一个容器。

### 简历能力点
容器化、多阶段构建、Nginx 反向代理、docker-compose 编排、镜像体积优化（6GB→600MB）、依赖版本锁定与可复现性。

## 阶段 ② PostgreSQL 持久化 ✅ 已完成

### 做了什么
- `docker-compose.yml` 增加 `db` 服务（`postgres:16-alpine`）+ 命名卷 `pgdata` 持久化 + `pg_isready` 健康检查；`api` 加 `depends_on: db(healthy)` 和 `DATABASE_URL`。
- 设计关系模型（**关系字段 + JSONB 混合**）：
  - `chats`（对话）：id、title、created_at、updated_at
  - `messages`（消息）：id、chat_id(外键, `ON DELETE CASCADE`)、seq、role、msg_id、`data(JSONB)`、created_at —— 一对多
  - 说明：路线图最初设想 `messages.content` 存纯文本，但实际 assistant 消息含 `answer/sources/trace/timing` 等富结构，纯文本会丢失。改用 **`data JSONB` 整条原样存**，配合 `role/seq` 等关系列（可索引、可排序、可过滤），前端字段零丢失、零改动。
  - 索引：`idx_messages_chat_id (chat_id, seq)`。
- 新增 `src/db.py`：psycopg3 连接池 + `init_db()` 建表（幂等）+ 4 个数据访问函数。`save_chat` 在**单个事务**内 upsert 对话 + 清旧消息 + 重插，保证一致性。
- 改造 `server.py` 的 4 个接口，从"读写 JSON 文件"改为"读写数据库"，返回结构保持一致：
  `list_chats / load_chat / save_chat / delete_chat`
- 编写迁移脚本 `scripts/migrate_chats_to_pg.py`：把现有 `results/chats/*.json` 幂等导入 PostgreSQL。
- 依赖：`requirements.txt` 增加 `psycopg[binary]` + `psycopg-pool`。

### 本地验证步骤
1. `docker compose up -d db`（先起库）
2. `.env` 里设 `DATABASE_URL=postgresql://rag:rag_pwd@localhost:5432/ragdb`
3. `python -m scripts.migrate_chats_to_pg`（导入旧对话）
4. 起后端 + 前端：历史对话还在、引用/PDF/轨迹正常、新消息能存能刷、删除生效
5. `docker compose down && docker compose up`：数据仍在（验证持久化）；`down -v` 才清空

### 解决的问题 & 作用
| 当前（JSON 文件） | PostgreSQL |
|---|---|
| 找关键词要逐个读文件 | 一条 SQL 查询 |
| 并发写可能损坏文件 | 事务保证一致性 |
| 文件多了扫描变慢 | 索引保持高效 |
| 难以做关联查询 | JOIN 轻松实现 |

**作用**：把"演示级的文件存储"升级为"工程级的数据持久化"，支持高效查询、并发安全、关联分析。

### 💡 一句话作用（大白话）
**把"演示级的文件存储"换成"真正的数据库"。**
- 现在聊天记录存成一个个 JSON 文件，小打小闹够用，但一多就出问题：搜索慢、并发写会冲突、做不了关联查询。
- 换成 PostgreSQL 后：一条 SQL 就能查、事务保证不冲突、加索引照样快。
- 这是从"玩具"到"产品"的关键一步——几乎所有真实系统都靠关系数据库存核心数据。面试问"数据怎么存的"，答"PostgreSQL + 关系建模"远比"存 JSON 文件"专业。

### 简历能力点
关系数据库建模、SQL、数据持久化、事务与并发、数据迁移（ETL）。

## 阶段 ③ Redis 缓存 ✅ 已完成

### 做了什么
- `docker-compose.yml` 增加 `redis` 服务（`redis:7-alpine`）+ AOF 持久化 + 命名卷 `redisdata` + `redis-cli ping` 健康检查；`api` 加 `depends_on: redis(healthy)` 和 `REDIS_URL`。
- 新增 `src/cache.py`：懒连接的全局 Redis 客户端 + `make_key / get_cached / set_cached`。
  - **缓存键** = `sha256(question + 排序后的 selected_paper_ids)`，选中范围相同即命中同一键。
  - **降级**：Redis 库缺失或连不上时静默关闭（首次失败后 `_disabled` 置位，避免每请求重试超时），绝不影响主流程。
- 改造 `server.py` 的 `/api/chat`（**A+ 方案**）：
  1. `history` 为空（独立问题）才走缓存；带上下文的追问一律实时跑，避免返回错答案。
  2. **命中** → 重放 `answer` / `eval` / `done` 三条 SSE 事件，`done` 带 `cached:true`，跳过整条 LangGraph 图（毫秒级、零 LLM 调用）。
  3. **未命中** → 跑完整流程 → 把 `parts / sources / eval` 写入 Redis（TTL=`CACHE_TTL`，默认 1h）。
- 前端：命中时 `App.jsx` 把 `cached` 存进 `timing`，`Chat.jsx` 在助手头部显示「⚡ 缓存命中」徽标（`styles.css`），演示时一眼看出第二次秒回。
- 依赖：`requirements.txt` 增加 `redis==5.2.1`。

### 本地验证步骤
1. `docker compose up -d redis`（先起缓存）
2. `.env` 里设 `REDIS_URL=redis://localhost:6379/0`（本地跑后端时）
3. 起后端 + 前端：同一问题问两次 → 第一次秒级、第二次毫秒级并显示「⚡ 缓存命中」
4. `docker exec <redis 容器> redis-cli keys 'chat:answer:*'` 能看到键，`ttl <key>` 看到过期倒计时

### 当初的设计（保留备查）
- 在 `/api/chat` 中加入缓存逻辑：
  1. 收到问题 → 先查 Redis 是否已有答案
  2. **命中** → 直接返回，跳过检索与 LLM 调用（毫秒级）
  3. **未命中** → 跑完整 RAG 流程 → 把"问题→答案"写入 Redis（设置 TTL 过期时间）

### 解决的问题 & 作用
| 作用 | 说明 |
|---|---|
| **响应提速** | 重复问题从秒级降到毫秒级 |
| **降低成本** | 命中缓存不调用 LLM，节省 token 费用 |
| **减轻负载** | 减少对检索与模型的重复计算 |
| **可控时效** | TTL 自动过期，避免答案陈旧 |

**作用**：用内存缓存为"昂贵且重复"的操作提速降本，是性能优化的经典手段。

### 💡 一句话作用（大白话）
**给"又慢又贵"的操作加缓存，重复问题秒回。**
- 每问一次，要跑检索 + 调 LLM，又慢（几秒到几十秒）又花钱（LLM 按 token 收费）。
- 加 Redis 后：同样的问题第二次问，直接从内存返回上次答案，毫秒级、不花一分钱 LLM 费用。
- 这是性能优化的经典套路——体现你不只"能实现功能"，还"懂怎么让它更快更省"。

### 简历能力点
缓存设计、Redis、性能优化、成本控制、TTL 失效策略。
