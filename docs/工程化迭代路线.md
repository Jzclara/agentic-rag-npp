# Agentic RAG 工程化迭代路线

> 把一个"能在本机跑的 RAG 应用"升级为"具备真实工程能力的完整项目"。
> 目标架构：前端(Nginx) → 后端(FastAPI + LangGraph) → 数据库(PostgreSQL) + 缓存(Redis)，全部由 docker-compose 一键启动。

```
              浏览器
                │
                ▼
        ┌───────────────┐
        │  web (Nginx)  │  容器1：托管前端页面 + 反向代理 /api
        └───────┬───────┘
                │
        ┌───────▼───────┐
        │  api (FastAPI)│  容器2：RAG 检索 + LangGraph 编排
        └───┬───────┬───┘
            │       │
      ┌─────▼──┐ ┌──▼─────┐
      │  db    │ │ redis  │  容器3、4：持久化 + 缓存
      │ (PG)   │ │        │
      └────────┘ └────────┘
```

## 阶段 ① Docker 化部署 ✅ 已完成

### 做了什么
- 后端 `Dockerfile`：基于 `python:3.11-slim`，层缓存优化（依赖与代码分层），CPU 版 PyTorch 裁剪。
- 前端 `web/Dockerfile`：多阶段构建（Node 打包 → Nginx 托管），最终镜像仅含静态产物。
- `web/nginx.conf`：托管静态页 + 反向代理 `/api` 到后端 + 支持 SSE 流式 + 放开上传体积限制。
- `docker-compose.yml`：编排 `api` 与 `web` 两个服务，含 healthcheck 解决启动时序依赖。
- 模型 / 索引 / 数据 / 结果通过挂载（volume）与镜像分离。

### 解决的问题 & 作用
| 作用 | 说明 |
|---|---|
| **环境可复现** | 任何机器 `docker compose up` 即可运行，告别"在我电脑上能跑" |
| **一键启动** | 一条命令拉起前后端，替代手动启动多个服务 |
| **镜像与数据分离** | 代码进镜像、模型/数据挂载，镜像小、数据可独立更新 |
| **部署标准化** | 与生产部署方式一致，可直接迁移到服务器 / 云 |

### 💡 一句话作用（大白话）
**把"只能在你电脑跑"变成"在任何机器一键就能跑"。**
- 以前换台电脑要重装 Python、装一堆依赖、配环境，各种"在我这能跑你那跑不了"；现在 `docker compose up` 一句话，前后端全起来，环境完全一致。
- 这是**工程化的地基**——后面加数据库、缓存，都只是往 compose 里再加一个容器。

### 简历能力点
容器化、多阶段构建、Nginx 反向代理、docker-compose 编排、镜像体积优化（6GB→600MB）、依赖版本锁定与可复现性。

## 阶段 ② PostgreSQL 持久化 ⬜ 进行中

### 要做什么
- `docker-compose.yml` 增加 `db` 服务（PostgreSQL 容器）+ 数据卷持久化。
- 设计关系模型：
  - `chats`（对话）：id、title、created_at、updated_at
  - `messages`（消息）：id、chat_id(外键)、role、content、created_at —— 一对多
- 改造 `server.py` 的 4 个接口，从"读写 JSON 文件"改为"读写数据库"：
  `list_chats / load_chat / save_chat / delete_chat`
- 编写迁移脚本：把现有 `results/chats/*.json` 导入 PostgreSQL。

### 解决的问题 & 作用
| 当前（JSON 文件） | PostgreSQL |
|---|---|
| 找关键词要逐个读文件 | 一条 SQL 查询 |
| 并发写可能损坏文件 | 事务保证一致性 |
| 文件多了扫描变慢 | 索引保持高效 |
| 难以做关联查询 | JOIN 轻松实现 |

**作用**：把"演示级的文件存储"升级为"工程级的数据持久化"，支持高效查询、并发安全、关联分析。

### 💡 一句话作用（大白话）
**把"演示级的文件存储"换成"真正的数据库"。**
- 现在聊天记录存成一个个 JSON 文件，小打小闹够用，但一多就出问题：搜索慢、并发写会冲突、做不了关联查询。
- 换成 PostgreSQL 后：一条 SQL 就能查、事务保证不冲突、加索引照样快。
- 这是从"玩具"到"产品"的关键一步——几乎所有真实系统都靠关系数据库存核心数据。面试问"数据怎么存的"，答"PostgreSQL + 关系建模"远比"存 JSON 文件"专业。

### 简历能力点
关系数据库建模、SQL、数据持久化、事务与并发、数据迁移（ETL）。

## 阶段 ③ Redis 缓存 ⬜ 待开始

### 要做什么
- `docker-compose.yml` 增加 `redis` 服务。
- 在 `/api/chat` 中加入缓存逻辑：
  1. 收到问题 → 先查 Redis 是否已有答案
  2. **命中** → 直接返回，跳过检索与 LLM 调用（毫秒级）
  3. **未命中** → 跑完整 RAG 流程 → 把"问题→答案"写入 Redis（设置 TTL 过期时间）

### 解决的问题 & 作用
| 作用 | 说明 |
|---|---|
| **响应提速** | 重复问题从秒级降到毫秒级 |
| **降低成本** | 命中缓存不调用 LLM，节省 token 费用 |
| **减轻负载** | 减少对检索与模型的重复计算 |
| **可控时效** | TTL 自动过期，避免答案陈旧 |

**作用**：用内存缓存为"昂贵且重复"的操作提速降本，是性能优化的经典手段。

### 💡 一句话作用（大白话）
**给"又慢又贵"的操作加缓存，重复问题秒回。**
- 每问一次，要跑检索 + 调 LLM，又慢（几秒到几十秒）又花钱（LLM 按 token 收费）。
- 加 Redis 后：同样的问题第二次问，直接从内存返回上次答案，毫秒级、不花一分钱 LLM 费用。
- 这是性能优化的经典套路——体现你不只"能实现功能"，还"懂怎么让它更快更省"。

### 简历能力点
缓存设计、Redis、性能优化、成本控制、TTL 失效策略。
