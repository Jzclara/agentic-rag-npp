# 学习笔记

## Embedding

**核心作用：** 把文本变成数字向量，让计算机能计算"两段文字有多相似"。embedding 质量直接影响检索召回效果——好的 embedding 能把语义相近的句子放在向量空间的近处，差的就找不到相关内容。

**不同 embedding 的主要差异：**

| 维度 | 说明 |
|------|------|
| 向量维度 | 维度越高信息越丰富，但存储和计算也更贵。`embedding-3` 是 2048 维，OpenAI `text-embedding-3-small` 是 1536 维 |
| 语言能力 | 中文语料用中文优化的 embedding 效果更好；Zhipu 对中文优化更多，OpenAI 中文能力也不差但不是重点 |
| 语义理解深度 | 顶级模型（如 `text-embedding-3-large`）在复杂语义匹配上更准 |
| 最大 token 长度 | 决定一个 chunk 最多能有多长 |

**本项目的选择：** 语料是英文学术论文，Zhipu `embedding-3` 因免费且调用方便作为起点。等第二阶段接入 Ragas 评估后，可以换其他 embedding 对比指标，用数据验证差异。

## 向量索引存储方式

`VectorStoreIndex.from_documents` 内部按顺序做三件事：分块 → 向量化 → 建索引。

**存储方式对比：**

| 方式 | 特点 | 适合场景 |
|------|------|---------|
| 内存（默认） | 无额外依赖，重启丢失 | 临时实验 |
| 本地磁盘持久化 | 写成 JSON 文件，下次直接加载 | 小语料，省 API 调用 |
| ChromaDB | 真正的向量数据库，支持元数据过滤、增量添加 | 中小项目，需要过滤功能 |
| Faiss | 百万级向量，速度极快，纯本地 | 大语料，Windows 安装易出问题 |
| Pinecone / Qdrant | 云端托管，生产级别 | 生产环境 |

**本项目当前方案：** 内存索引 + `persist()` 写到 `index/` 目录，第一次构建后不再重复调 embedding API。

**ChromaDB vs 当前方案的核心区别：** ChromaDB 支持元数据过滤（如只搜索某篇论文），当前方案更轻量但功能少。

**换存储的时机：** 等第四阶段，用 Ragas 指标验证换存储前后有无变化，再决定是否迁移。

## 对话历史传给模型的两种方式

调用 LLM 时，如果需要模型理解之前的对话（比如用户说了"these methods"，模型要知道指的是哪些 methods），就必须把对话历史传给它。有两种写法：

**方式 1：拼进 prompt 文本里（本项目使用的方式）**

把历史对话转成一段文本字符串，和当前问题一起塞在一条 user 消息里发出去：

```python
prompt = (
    f"Conversation history:\n{history_str}\n\n"
    f"Retrieved context:\n{context_str}\n\n"
    f"Current question:\n{query}\n\n"
)

messages=[
    {"role": "system", "content": "你是一个 RAG 助手"},
    {"role": "user", "content": prompt},
]
```

messages 里只有 system + user 两条，但模型能从 prompt 文本中读到完整历史。

**方式 2：用 messages 列表传（OpenAI 官方推荐的多轮写法）**

每轮对话单独一条 message，role 交替排列：

```python
messages=[
    {"role": "system", "content": "你是一个 RAG 助手"},
    {"role": "user", "content": "What methods are used for fault diagnosis?"},
    {"role": "assistant", "content": "Methods include empirical modeling..."},
    {"role": "user", "content": "Which of these are data-driven?"},
]
```

**两种方式的区别：**

| | 方式 1（拼文本） | 方式 2（messages 列表） |
|---|---|---|
| 写法 | 历史拼成字符串，塞进 user prompt | 每轮对话一条 message，role 交替 |
| messages 里有 assistant 吗 | 没有，历史藏在 user 文本里 | 有，每条旧回复都是 assistant |
| 灵活性 | 高，可以自由控制 prompt 格式 | 结构化，模型原生支持 |
| 适合场景 | RAG 场景（需要同时传 context + history） | 纯对话场景（不需要额外上下文） |

**为什么本项目选方式 1：** 因为 RAG 的 prompt 里不只有对话历史，还要拼检索上下文（retrieved context）。如果用方式 2，检索上下文不好塞进 messages 的 role 结构里。方式 1 可以自由拼接 history + context + question，更灵活。

**核心理解：** 不是"没传 assistant 就不是多轮"，而是历史被拼在文本里了，模型照样能看到。

## Parent-Child Chunk（父子分块）

**要解决的问题：** chunk 大小的矛盾——小 chunk 检索匹配精准但上下文不完整，大 chunk 上下文完整但匹配不够精准。Parent-Child Chunk 的思路是两个优势都要。

**做法：** 先把文档切成大块（parent，如 1024 token），再把每个 parent 切成小块（child，如 256 token）。索引建在 child 上，检索也用 child 匹配，但命中后返回给 LLM 的是对应 parent 的完整文本。

**和直接切小块的区别：**

直接切 256 的小块，每个 chunk 彼此独立，没有从属关系：

```
文档 → [chunk1][chunk2][chunk3][chunk4][chunk5][chunk6] ...
```

检索命中 chunk3 后只能拿到 256 token，前后文丢失。

先切大块再切小块，每个 child 知道自己属于哪个 parent：

```
文档 → [parent A: 1024 token]     [parent B: 1024 token]
              ↓                           ↓
      [child1][child2][child3]    [child4][child5][child6]
```

检索命中 child2 后，返回整个 parent A 的 1024 token，child2 和 child3 的前后文不会丢失。

**举例：** 假设论文中一段话先介绍了 LSTM 的网络结构（前半段），再说了实验结果（后半段）。直接切 256 可能把结构和实验切成两个独立 chunk，检索命中"LSTM 结构"后 LLM 看不到实验结果。用 parent-child，不管命中哪个 child，LLM 都能看到完整的结构 + 实验结果。

**一句话总结：** 用小块的精准匹配能力 + 大块的完整上下文，解决 chunk 大小的两难问题。

## 混合检索（Hybrid Search）

**要解决的问题：** 纯向量检索擅长语义匹配（"abnormal event detection" ≈ "anomaly identification"），但对精确术语匹配弱（用户搜 "MFM"，向量可能找到语义相近但不含这个词的内容）。BM25 关键词检索刚好相反，精确匹配强但不懂语义。混合检索把两者结合，互补短板。

**做法：** 同一个问题同时走两路检索，各自返回候选结果，再合并成一个排序：

```
用户问题 ──┬── 向量检索 → 候选 A 组（语义相似的）
           └── BM25 检索 → 候选 B 组（关键词匹配的）
                          ↓
                   RRF 合并去重排序 → 最终结果
```

### Reciprocal Rank Fusion (RRF) 合并策略

两路检索结果怎么合成一个排序？对每个 chunk 计算 RRF 得分：

```
得分 = Σ 1/(k + rank)
```

- **rank**：该 chunk 在某路检索中的排名位置（从 1 开始）
- **k**：固定常数，通常取 60，作用是压平排名差距，防止某一路排名特别高就完全压过另一路

举例：假设 chunk A 在向量检索排第 1，在 BM25 排第 3：

```
得分 = 1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323
```

假设 chunk B 只被向量检索找到，排第 2，BM25 没有命中：

```
得分 = 1/(60+2) = 0.0161
```

chunk A 两路都排前面所以得分高，chunk B 只被一路找到但也不会丢。

**核心价值：** 两路都认为好的排最前，只被一路找到的也保留。既不丢语义相关的结果，也不丢精确匹配的结果。

## RAG 整体架构：离线层与在线层

RAG 系统可以分为两层来理解：

### 离线层（提前做好，只做一次）

```
原始文档 → 文档加载 → 切块 → 向量化（embedding） → 存入索引/知识库
```

这一层把文档变成可检索的状态，做完后索引存在磁盘上，后续不用重复跑。

### 在线层（每次用户提问都走一遍）

```
用户问题 → 问题处理 → 向量化 → 检索 → 后处理 → 大模型生成 → 输出
```

| 步骤 | 做什么 |
|---|---|
| 问题处理 | query rewrite（改写问题、解析指代词）、query decomposition（拆分复杂问题） |
| 向量化 | 把问题变成向量，和索引里的 chunk 向量做相似度比较 |
| 检索 | 向量检索、BM25 关键词检索、或两者混合 |
| 后处理 | rerank 重排序、parent 文本替换、去重、过滤 |
| 大模型生成 | 把问题 + 检索上下文拼成 prompt 调 LLM 生成回答 |

第四阶段的优化（rerank、parent-child、hybrid search、metadata filtering）主要集中在检索和后处理这两个环节。
