# Agentic RAG 项目演示

## 一、项目概述

从零搭建的面向学术论文的 Agentic RAG 系统，用 LlamaIndex 做检索层、LangGraph 做 Agent 编排、Ragas 做量化评估，并逐步实现了 rerank、混合检索、parent-child 分块等检索优化，用评估数据验证每一步优化的效果。

语料为 8 篇核电站（NPP）领域的英文学术论文，覆盖故障诊断、异常检测、风险评估、强化学习等方向。

## 二、系统架构

```
┌─────────────────────────────────────┐
│         Agent 编排层（LangGraph）      │
│  rewrite → retrieve → grade → generate │
│         条件路由 / 重试 / 兜底          │
├─────────────────────────────────────┤
│          检索层（LlamaIndex）          │
│  文档加载 → 切块 → embedding → 向量索引  │
│  向量检索 / BM25 / rerank / parent-child │
├─────────────────────────────────────┤
│          评估层（Ragas）              │
│  faithfulness / answer_relevancy      │
│  固定测试集，量化对比不同版本            │
└─────────────────────────────────────┘
```

三层解耦：改检索不影响编排，改编排不影响评估，每一层可以独立替换和优化。

### 离线层（只做一次）

```
原始 PDF → 文档加载(pypdf) → 切块(SentenceSplitter) → 向量化(BGE embedding) → 存入索引
```

### 在线层（每次提问都走一遍）

```
用户问题 → 问题改写(rewrite) → 向量化 → 检索 → 后处理(rerank/RRF合并) → 大模型生成 → 输出
```

## 三、各层技术栈

### 检索层（LlamaIndex）

| 环节 | 具体技术 | 说明 |
|---|---|---|
| PDF 解析 | pypdf | 按页提取文本，保留文件名和页码元数据 |
| 文档对象 | LlamaIndex Document | 把每页文本包装成 LlamaIndex 能处理的格式 |
| 文本切块 | LlamaIndex SentenceSplitter | 按句子边界切分，chunk_size=512，overlap=50，保证语义完整性 |
| Embedding | BAAI/bge-small-en-v1.5 | 本地 HuggingFace 模型，通过 LlamaIndex 的 HuggingFaceEmbedding 加载 |
| 向量索引 | LlamaIndex VectorStoreIndex | 内存索引 + 持久化到磁盘，首次构建后直接加载 |
| 向量检索 | LlamaIndex as_retriever | 余弦相似度 top-k 检索 |
| 关键词检索 | rank_bm25 (BM25Okapi) | 基于词频的关键词匹配，和向量检索互补 |
| 重排序 | BAAI/bge-reranker-base | cross-encoder 模型，通过 sentence-transformers 的 CrossEncoder 加载 |
| 结果融合 | RRF（自己实现） | Reciprocal Rank Fusion，合并向量和 BM25 两路结果 |

### Agent 编排层（LangGraph）

| 环节 | 具体技术 | 说明 |
|---|---|---|
| 图框架 | LangGraph StateGraph | 定义节点、边、条件路由 |
| 状态管理 | Python TypedDict | AgentState 定义图中流转的数据结构 |
| LLM 调用 | DeepSeek (deepseek-v4-flash) | 通过 OpenAI SDK 兼容接口调用，用于 rewrite、grade、generate 三个节点 |

### 评估层（Ragas）

| 环节 | 具体技术 | 说明 |
|---|---|---|
| 评估框架 | Ragas | 专门用于 RAG 系统评估的开源库 |
| 评估用 LLM | DeepSeek | Ragas 内部用 LLM 判断 faithfulness |
| 评估用 Embedding | BAAI/bge-small-en-v1.5 | Ragas 内部用 embedding 计算 answer_relevancy |
| 数据集 | HuggingFace datasets | 把评估数据转成 Ragas 需要的 Dataset 格式 |

### 基础设施

| 环节 | 具体技术 |
|---|---|
| 语言 | Python 3.11 |
| 包管理 | pip + venv |
| 环境变量 | python-dotenv |
| 版本控制 | Git |

## 四、检索优化方法

第四阶段实现了四种检索增强方法，每次只改一个变量，用 Ragas 评估对比效果。

### 1. Rerank（重排序）

解决向量粗排有噪声的问题。先 top-10 粗召回，再用 cross-encoder（bge-reranker-base）精排取 top-5。cross-encoder 同时看 query 和 chunk，比余弦相似度更准。

```
向量检索 top-10（粗召回） → cross-encoder 重新打分 → 取 top-5（精排）
```

### 2. Parent-Child Chunk（父子分块）

解决 chunk 大小的两难问题：小块匹配精准但上下文断裂，大块上下文完整但匹配不精准。用 256 token 的 child 做检索匹配，命中后返回对应 1024 token 的 parent 文本。

```
文档 → 切 parent 大块(1024) → 每个 parent 再切 child 小块(256)
索引建在 child 上 → 检索命中 child → 返回对应 parent 给 LLM
```

### 3. Hybrid Search（混合检索）

解决纯向量检索对精确术语匹配弱的问题。向量检索 + BM25 关键词检索两路召回，用 RRF（Reciprocal Rank Fusion）合并。

```
用户问题 ──┬── 向量检索 → top-10
           └── BM25 检索 → top-10
                          ↓
                   RRF 合并 → top-10 候选
                          ↓
                   Rerank 精排 → top-5
```

RRF 公式：每个 chunk 的得分 = Σ 1/(k + rank)，两路都排前面的得分最高，只被一路找到的也不会丢。

### 4. Metadata Filtering（元数据过滤）

评估后决定不实施。原因：8 篇论文全是核电领域，主题有交叉，打标签不准反而会过滤掉正确结果。元数据过滤更适合文档量大、主题明确隔离的场景（如多租户系统、按时间过滤、按文档类型过滤等客观属性）。

不是所有优化都该做，要根据数据特点判断。

## 五、Agent 编排流程

```
rewrite（改写问题，解析指代词）
   ↓
retrieve（检索文档片段）
   ↓
grade（判断检索内容是否和问题相关）
   ├── 相关 → generate（生成回答）→ 结束
   └── 不相关 → increment_retry → rewrite（改写后重试）
                    └── 重试次数用完 → fallback（兜底回答）→ 结束
```

### 关键经验：Agent 不等于更好

实测发现 Agentic RAG 的 faithfulness 一度低于 baseline。原因是 grade 节点的 prompt 判断标准太严格（"上下文是否足够"），导致频繁误触重试，改写后的问题偏离原意。

修复方案：把 grade 从"是否足够回答"改成"是否包含相关信息"，只拦截完全不相关的情况，其余放行。修复后分数回升。

结论：Agent 的价值取决于每个判断节点的准确性。判断不准，不如不判断。

## 六、评估体系

### 评估指标

| 指标 | 含义 |
|---|---|
| faithfulness | 答案是否被检索内容支持，衡量有没有"瞎编" |
| answer_relevancy | 答案是否真正回应了用户问题 |

### 评估模式

| 模式 | 流程 | 用途 |
|---|---|---|
| 模式 1 | 从已有对话记录评估 | 评估手动跑过的对话质量 |
| 模式 2 | 从 testset.jsonl 跑 baseline | 标准化 baseline 分数，作为对照组 |
| 模式 3 | 从 testset.jsonl 跑 Agentic RAG | 评估 Agent 图流程 + 各种检索优化 |

### 测试集

testset.jsonl 包含 8 组多轮对话，每组 4 个递进问题（共 32 题），覆盖核电领域各主题。后续问题引用前文（如 "these approaches"、"their limitations"），用于测试 query rewrite 能力。

### 评估原则

- 固定测试集，每次改进后重跑，分数可直接对比
- 每次只改一个变量，隔离单一优化的效果
- 同一版本多次运行取平均，排除 LLM 随机性（样本量小时尤其重要）

## 八、面试高频问题与回答思路

### Q: 为什么选这些技术栈？

LlamaIndex 的 RAG 能力成熟，适合深入理解检索细节；LangGraph 让流程从线性变成可控的图结构；Ragas 提供标准化的 RAG 评估指标。三者各负责一层，解耦清晰。

### Q: chunk_size 为什么选 512？

经验起点。太小（128）语义不完整，太大（1024）检索不够精准。512 对学术论文段落比较合适。后续通过 Ragas 评估对比了不同 chunk size 的效果，用数据决定而不是靠感觉。

### Q: 加了 Agent 效果一定更好吗？

不一定。我实测 Agentic RAG 的 faithfulness 一度低于 baseline，原因是 grade 节点 prompt 判断太严格，导致频繁误触重试。修复 prompt 标准后分数回升。Agent 的价值取决于每个判断节点的准确性，判断不准不如不判断。

### Q: 为什么没做元数据过滤？

评估了语料特点后决定不做。8 篇论文全是核电领域，主题有交叉，打标签不准反而会丢正确结果。元数据过滤适合文档量大、属性明确的场景。不是所有优化都该做，要根据数据特点判断。

### Q: 样本量够吗？

32 个问题存在波动，实验中观察到同一版本两次跑分差距可以到 0.25。生产环境需要更大测试集和多次运行取平均。但作为学习项目，这个体量足够验证优化方向是否正确。

### Q: 如果要做成产品，还需要什么？

- 增量索引（现在是全量重建，加新文档要重新 embedding 所有内容）
- 更大的测试集 + 多次运行取平均
- 前后端分离（FastAPI + 前端框架），支持多用户
- 更好的 embedding 模型和 LLM
- 日志监控和错误处理
